# Author

Use this guide to create a playbook, iterate on a draft, or publish a new immutable version. Do not author a playbook merely to store one case's facts; those belong on the case as records.

## Search first

Search existing playbooks before creating one. Improve a fitting playbook when the outcome, audience, and lifecycle match. Create a new one when those boundaries differ materially. If the request is "turn this case into guidance," extract the repeatable procedure and file it through [Improve](./improve.md) when a playbook already exists.

## Write the definition

Write steps as judgment-sized guidance rather than tiny commands or a rigid
execution graph. Keep run-specific facts in cases and large background
material in referenced documents.

## Keep step identity stable

Preserve an existing step's ID when changing its wording or order so evidence
and suggestions tied to that step still point to the same concept. Treat a
genuinely new step as a new identity.

## Reference resources as hints

Treat each resource hint as a discovery hint, not an installation or trust decision. Never put credentials or expiring signed URLs in one. Prefer a pinned or conservative selector for shared and audited work; resolution, permission, and sandboxing belong to the runtime.

## Iterate with a draft

Review a draft's current content before publishing; if another editor changes
it after review, compare and reconsider the newer draft. A draft is an owner's
or editor's in-progress change, while a suggestion is a reviewable proposal
from another reader; see [Improve](./improve.md).

## Publish safely

After a conflict, compare the latest version with the intended change and
merge deliberately. Show the content diff before publishing on someone's
behalf, then verify the published definition and access. If the change cannot
be published through an authorized surface, propose it as a suggestion.
