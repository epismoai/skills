# Share and Publish

Use this guide whenever the requested result changes who can access a pack or how it is presented to others.

## Choose the Access Change

- Keep **personal** scope for material owned and used by one person.
- Use **project** scope for work belonging to a project.
- Use direct sharing for a known person or limited audience.
- Use **public** visibility only to publish for community discovery.

Sharing and publication are different actions. Do not substitute one for the other.

Preserve current access when access is not part of the request.

## Authorization Boundary

Require explicit user intent before:

- making private material public;
- deprecating a public workflow;
- deleting a whole pack;
- replacing access beyond the requested audience.

A direct request for the exact action counts as explicit intent. Do not ask twice, and do not infer authorization from an adjacent request.

## Prepare for Sharing

Before expanding access:

- remove secrets, credentials, private identifiers, and unnecessary personal data;
- remove internal-only details the audience should not receive;
- make the title and description understandable to the intended audience;
- ensure referenced material is accessible to the same audience or clearly marked unavailable;
- confirm the selected workspace and project.

For public workflows, also verify that steps are reusable, dependencies are valid, and organization-specific assumptions are explained or removed.

For public context, ensure an outside reader can interpret it safely without hidden project history.

## Publish, Update, or Deprecate

Publish an existing private pack when continuity is useful. Create a distinct pack when the audience, subject, outcome, or lifecycle differs materially.

Update an existing public pack when improving the same artifact.

Deprecate a public workflow only with an explicit reason. Prefer deprecation over deletion when users may still rely on its reference.

After the change, verify visibility and audience, then return the canonical reference or share link exposed by the current surface.

## Aliases and References

Use an alias when a stable human-readable reference improves repeated use. An alias points to a pack; it is not a copy and does not grant access.

Pass supported IDs, aliases, and URLs through the current surface rather than extracting or rewriting identifiers manually.

Before deleting or repointing an alias, check whether the user intends to change the name, the target, or the underlying pack. These are separate actions.
